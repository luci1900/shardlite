# shardlite internals

How the node works: its architecture and the rules that keep it correct. It describes the overall shape and the details that matter, and leaves out what the code says plainly. The app-facing behaviour is in the [guide](guide.md), and the protocol's models are in [specs/](../specs/).

## Terms

| Term | Meaning |
|---|---|
| **Node lease** | An object each node holds and renews. Every ownership depends on it. |
| **Node journal** | Numbered segments, one per flush interval, holding the node's shards' commits since their last snapshots: the shared WAL. |
| **Snapshot** | A shard as of one commit, as immutable LTX files: a base and deltas. An inactive shard lives only in its snapshot. |
| **Manifest** | A shard's state in storage: owner and epoch, files, the journal holding later commits, when it next needs waking. |
| **Reminder index** | Empty objects saying a shard may need waking at a minute. The dispatcher reads them. |
| **Orphan index** | Empty objects saying a generation of a shard may hold LTX files no manifest lists. The collector reads them. |
| **Reconciler** | A due index (the reminder or the orphan index) and the handler for its entries, run by one loop on every node. |
| **Lane** | One of 16 hash classes of shard names. A shard's index entries, LTX files and manifest (`state/shards/{lane}/{kind}/{id}`) have keys that start with its lane, and each lane's index entries are handled by the node that ranks first for it. |

The other terms are in the [overview](overview.md#concepts).

## The shape of a node

The node is one Go process. It reads each shard's WAL itself and encodes what it reads as [LTX](https://github.com/superfly/ltx) files. Capture is driven, never polled: the flush loop spots commits by mapping each active shard's wal-index header, which SQLite updates on every commit, so a sync costs microseconds. Nothing shard-sized lives in memory: tails, deltas, restores and rebases all go through unnamed files in `{data}/.tmp`.

Blob storage is the source of truth: manifests, LTX files, one journal per node, the reminder and orphan indexes. The node's disk holds only the working copy of each active shard. A shard that is deactivated is released and its files are deleted, so a node owns exactly the shards it is serving, and an inactive shard is in storage and nowhere else.

Leases and manifests are objects changed with conditional writes, which are linearizable on every supported store, so there is no leader, no election and no set of stable nodes. Every write carries a CRC32 the store verifies and every read checks the checksum the store returns, so corruption fails the read that finds it. Callers go through `blob.Store`, which makes writes safe to retry (see [Lost responses](#lost-responses)). The node checks its store's conditional writes on a scratch key at startup and refuses to start if they misbehave.

Only two things live outside shards: a lease (which node is alive, in which epoch) and a journal (commits durable before any file holds them), neither of which can live inside a database whose owner they decide. Everything else is a **shard**: a database stored the same way, with a kind, the claim rule and a lifecycle. The test for anything new: state shared across nodes goes in a shard, an entry written while no owner can be relied on is an index object (see [The reminder index](#reminder-index)), and only what a shard needs to exist is a primitive.

## Failing loudly

The dangerous failure is not the crash, which is loud and costs a restart, but the wrong answer nothing reports: a segment with the right size and wrong bytes, an acknowledgement for a write that is not there. Two rules decide much of the node's shape: every mechanism must report its own failure, and every mechanism we write ourselves must be one the fault rig can make fail (capture's read of a WAL, the temporary files, the writer's landing of a segment, the applier's write of a page), each checked by killing a node mid-step.

A closed set answers for its zero value under one of two policies: the zero is an inherently safe member that causes no action (a position of 0 is nothing yet, no store, nothing written), or it is a named `Unknown` that `Valid()` rejects and every switch handles, so it cannot land in a default written for another reason. A zero that is the first real state, or one that enables an action, is not allowed, and a decoder rejects an unknown value rather than mapping it onto the zero, so a newer node's state fails loudly instead of being downgraded. Each package that owns a closed set pins the policy in a zero-value test, and the linter's `mapliteral` mode fails an enum-keyed table missing a member.

## Ownership and fencing

A lease alone can't prevent two writers (a pause, a delay), so the storage must reject a stale owner's writes, as in Kleppmann's [How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html). Here that is the journals (one writer each) with the manifests, specified in Quint.

### Node leases

Each node holds one lease, renewed by CAS every few seconds, carrying its epoch, address, whether it serves and the range of its journal still needed. A shard's ownership is valid only while its owner's lease is, so one expired lease releases all of a crashed node's shards.

- **Elapsed time, not timestamps.** The holder treats its lease as expired at the start of its last successful renewal plus the TTL less a fifth, by its own clocks; another node, once it has seen the lease unchanged for a TTL on its own monotonic clock. Leases need clock rates that agree, not synchronised clocks, and a node that loses its lease exits and restarts as from a crash.
- **Checking the clock.** The node compares its clock with the `Date` header of the store's responses. An offset over a second warns and one over the lease TTL stops the start. It fails nothing else: `none` answers rest on working clocks, and this is where an operator learns that one is not.
- **Noticing dead nodes.** Nodes list `state/leases/` in turn, so the cluster lists about every 2 seconds. A listing's last-modified times are a hint: seeing an old one, the node reads the lease, looks again a TTL later and adopts only if it is unchanged. A released lease is dead at that read. A node found dead stays dead through its adopter's writes to its lease (the mark and the finish), which are not renewals: when the listing shows a dead node's lease changed, the scan reads it again, and only a new epoch (the node restarted) counts it live. So the owner cache, the placer and the ranking of lanes never take an adopted node for a live one.

### Manifest

A manifest is created with a conditional create and changed only by CAS, at ownership changes and snapshots, never on writes or activating an owned shard (its fields are in `internal/shardfile/manifest.go`).

- **`next_reminder`** is set by the owner's deltas, rebases and deactivations, its entry in the reminder index created first. Adoption's deltas set it to now.
- **`rev`** goes up on every write, so no two versions share bytes: a manifest released and claimed again by the same node would otherwise return to an earlier version, which the pruning rule reads differently.
- Ownership is invalid if `node_epoch` doesn't match the owner's current lease or that lease has expired, and a shard deleted and created again gets a new `generation`, so it never reads the old shard's files.

### Fencing

- Each journal has one writer. Segments are numbered and created once, and a writer finding its number taken has been fenced and stops for good.
- An adopter fences a dead node's journal with an empty segment at the first free number after the lease's recorded range; a zombie can then only write below the fence, where nothing is part of any shard's history. The fence in storage decides the journal.
- A zombie's LTX files count once a manifest CAS adopts them, and a stale owner's CAS fails once anyone else has changed the manifest.
- This needs no listings: segments are found by number, and single-object reads are strongly consistent on every store with conditional writes.

### Confirming ownership

A `storage` answer leaves once ownership is confirmed after the answer was read: evidence, begun after the chunk was read from the app, that no other node can yet have acknowledged anything for the node's shards. The rule underneath is that every way another node takes a shard from a live owner writes the lease first: an adoption marks it, a restart takes a new epoch, a release marks it adopted, and a deactivation (at idle or at a stop) is started by the owner, which stops serving the shard first. So a lease that still shows this incarnation's epoch, not released, not marked by another incarnation and not adopted up to the epoch, means nobody has begun a takeover. Two kinds of evidence count:

- **A segment created in storage** by a flush cycle that began after the chunk was read. An adopter marks the lease, fetches, then fences, and a new owner claims only after the fence, so a segment that lands came before any other owner's acknowledgement. This is why output after a commit needs no lease read.
- **A read of the node's own lease** begun after the chunk was read. The `Confirmer` (`internal/lease`) runs at most one at a time and a waiter joins only a read that begins after it arrived, so on an idle node a burst of reads shares one GET and under write load the segments release the waiters. The lease's expiry is left out of the condition, since the clocks are what this replaces.

A confirmation that finds the lease taken fails the keeper with `ErrLost`, so the node stops and restarts as from a crash, and one that cannot reach the store fails the answer with `503`, never answering unconfirmed. A request confirms once: its first chunk is read after the request began, and the shard's file only grows while the request holds it. Streams are therefore linearizable at their start and then follow the node's copy until it notices the loss of the shard. `none` answers are not confirmed.

### Consistency

Per shard, every read and write is linearizable on the `storage` tier, and on `none` until the node crashes (see the [guide](guide.md#consistency)). Writes: one owner per shard, SQLite's commit order, an acknowledgement waiting for the commit to reach the journal, and a zombie's acknowledged commits below the fence its adopter reads. Reads on `storage` are confirmed, so they need no assumption about clocks or pauses. Reads on `none` check the node's lease before output leaves, and claiming a dead owner's shard needs an adopter that watched the lease stay unchanged for a TTL and fenced the journal, so for those clock rates must agree within the lease's margin (20%) and no pause may hide from the machine's own clocks.

### Lost responses

Any write can succeed while its response is lost. `blob.Store` stores a write id with each object and, when a retry meets "exists" or "conflict", reads it back to recognise its own attempt, and `journal.Store` gives the journals the same, so a caller sees success, a conflict, or an unknown outcome. The journal writer retries the same segment until the outcome is known, and a manifest handle compares the stored manifest with the one it tried. The node never retries a request the app may have seen.

### Takeover

- **Deactivation** (at the shard's idle timeout, or at a stop): the owner lets the shard go and gives it up, and the next node to need it claims and restores. A shard is deactivated and released in one manifest update, the one that records its last delta (a shard with no tail has its next reminder and the release written together), and its files are deleted, so a deactivation costs one write whether or not there was anything to record. The update may have landed or not when its outcome is unknown, and either answer is unsafe to act on: if it landed the shard is unowned with its tail only in the journal, so serving it again is wrong, and if it did not the shard is still ours, so dropping it is wrong. The node therefore asks again until it learns the outcome (the update is the same each time and the handle reads the stored manifest first) and serves or drops nothing on a guess. That keeps the shard closed meanwhile, so in a storage brownout a shard that has just gone idle keeps its requests waiting until storage answers, and they are served once it does, by whichever node claims the shard. If the node stops first it abandons the shard, keeps the lease and leaves either outcome to adoption (an unowned manifest has nothing in a journal, and a still-owned one has the tail there). It is the shard's own loop that does it, with no dispatch, target or mark. Stopping anywhere is safe because nothing but the update changes hands: before it the shard is as it was, and after it the shard is unowned and the next request claims it wherever it lands.
- **Drain** (scaling down, a restart) is the first part of a stop that was asked for (the context ending, as on SIGTERM). Readiness fails (`503 draining`), the node's answers and forwards say `Shardlite-Placement: avoid`, which its peers learn and place nothing on, and every claim that reaches the node is placed on another node whatever its origin (a client's request, a call, a forward or a dispatch), as a forward or as a `421` naming the pick. With no other node to pick (none live, or each avoided) the node claims for itself. The stop then shuts the public server, lets go of every shard (each a deactivation) and releases the lease, with the peer and control listeners still up, so a forward or call for a shard on its way out waits on its entry, finds none and is answered by another node. Nothing is marked or moved ahead of time: each shard is claimed elsewhere at its own next request, so the takeover is spread by traffic and the dispatcher only acts on reminders when they are due. A shard with connections is let go of at the stop, and its clients reconnect through the load balancer to another node, which claims it where they are. A node that fails (a lost lease, a fenced writer, a failed service) doesn't drain: it stops at once, lets nothing go and keeps its lease, and its shards wait for adoption. After a stop the node stays listed as alive until the lease scan finds its released lease (about a TTL), so its lanes wait that long and a forward to it gets `503` with `Retry-After: 1` until then.
- **Crash.** A node whose lease has expired is adopted by the first live node to notice, every step a conditional write safe to redo: **mark** the lease as being adopted, **fence** the dead journal, **read** the footers up to the fence, then per shard still naming the dead journal create a reminder entry due now and add the tail as a delta by CAS (with `next_reminder` now and the journal cleared), **finish** by CAS on the lease (adopted to the dead epoch, the journal range past the fence), and **sweep** the segments below the fence, fences staying. What a dead node held only on its own disk is gone. The shards it had released when they went idle name nobody, so they are claimable at once and the adoption only concerns the ones it was serving.
- **Restart** is treated as a crash, one recovery path: the node takes a new epoch, adopts its own journal before serving anything and starts its writer after the fence with nothing on disk. A `none` commit that storage did not yet have is lost in any crash of the node, process or host. While another node is adopting it and it looks alive, the restarting node waits.

The reminder entry comes before the delta because journal expiry deletes covered segments without checking any lease: an adopter dying between the two would leave a shard nobody knows to wake (`noAdoptionEntry` in `specs/dispatch.qnt`). A claim copies nothing between journals. The dead node's shards keep it as their owner until nothing of them can be in its journal (the manifest names no journal, or the node adopted up to the owner's epoch), and since no timestamp decides it, a lease that looks expired still owns its shards until then.

## Capture and snapshots

### The read rule

While a shard is captured, the node holds one read transaction begun under the write lock right after a sync and a checkpoint that copied everything, so it gets read mark 0. SQLite then copies no frame into the database file and never restarts the WAL while a frame is waiting to be copied, the only restarts it allows coming after the node's own checkpoint (the app's next write, or its restart or truncating checkpoint), when every frame of the old WAL is captured. So no uncaptured frame is ever copied or lost.

- **The locked restart.** While the transaction is held the WAL only grows, so past a threshold of frames the node takes the write lock, syncs, ends the transaction, has everything copied in (a passive checkpoint) and begins a new one. It must be passive, since a truncating checkpoint can't run under the node's own lock and frames committed in the gap would be wiped uncaptured.
- **The app's checkpoints do nothing while a shard is captured:** a passive one copies nothing, and a restart or truncating one answers `SQLITE_BUSY`.

Each sync appends the LTX file it encodes to the shard's tail, append-only unnamed files in `{data}/.tmp` and the ranges of them holding the commits not yet in a delta. `specs/capture.qnt` checks the rule: every committed frame is in a captured file before it can leave the WAL (`noLoss`), the files replayed give the database at the captured end (`replay`), and a snapshot gives the database at the position it began (`snapOk`).

### Checksums

Every LTX file carries the database's checksum before it and after it (LTX's whole-database checksum, the XOR of each page's CRC with its number). Capture keeps every page's CRC in memory, so the checksums cost one CRC per changed page. Deltas check the chain, each file's before being the one before's after. A rebase compares capture's checksum with the snapshot's, and a mismatch (capture went wrong) is logged and counted, the rebase written anyway since it is the database as SQLite reads it. A file without checksums fails like any broken file. A restore verifies every file, and the first mismatch fails it with the file named: the shard is not served and nothing is deleted, so an operator has every file.

### Node journals and snapshots

The same split as a database's WAL and data files: the journal the shared WAL of a node's shards, the LTX files each shard's data files, a snapshot the checkpoint. The journal's store is `internal/journal`: numbered segments created once, durable before the create returns, read by number (a head of size 0 is a fence), behind an interface with a conformance suite. Every create carries the write-id handling of [Lost responses](#lost-responses), so a lost response costs a retry, never a fence.

- **Segments.** Every flush interval one segment, a footer naming its shards, the body composed from the LTX files capture queued so the bytes are written once.
- **Snapshots as deltas.** When a shard deactivates, or its tail is old or large, the node writes the pages captured since the last snapshot as one delta and adds it by CAS, without reading the database file, so a shard that is not active never has a tail and the lease's journal range only covers active shards.
- **Rebasing.** Once a manifest lists many files, the next snapshot is a full copy of the live database as a new base, bounding how many files a restore reads. A few run at once per node.
- **Cleaning the journal.** Each node deletes its own non-empty segments once a day old, and an alert comes long before if a tail is old, since nothing tracks which segments are in use. Fences are never deleted, since a paused zombie could then write into a freed number.

## Durability gates

- A chunk the app wrote is held until a flush that started after it was read has captured it and the store its tier names has what the flush queued, since every flush captures every active shard's commits up to its start. Chunks waiting together share one flush (group commit).
- `none` waits for nothing past the lease check, and `storage` for the PUT: a flush that started after the chunk was read has to have created its segment. A `sync` outside the set is an error, never a tier that waits for nothing.
- Every chunk first needs the node's lease to be good, and a flush that completed after the lease ran out acknowledges nothing.
- A `storage` chunk then waits to be confirmed unless its request has been (see [Confirming ownership](#confirming-ownership)). A chunk that waited for its commit's segment is confirmed by it unless the cycle that passed created none.
- A call to another shard is bytes leaving the caller, so it waits for the caller's commits to meet its kind's tier.

## Data and state

| Role | Objects | Changes by | Rule |
|---|---|---|---|
| **Data** | journal segments, LTX files | create once, delete by garbage collection | never modified |
| **State** | leases, manifests | compare-and-swap by the owner | the truth, naming the data it points at |
| **Index** | due index entries (the reminder and orphan indexes) | created by anyone before the write they are for, moved and deleted by the index's [reconciler](#reconcilers) | deleted only by the index's own rule, once the truth they point at no longer needs them |

Journal segments go to blob storage, which is the only copy: a restore, an adoption and a restart all read it, and the fence is created there. Listings stay per prefix (leases, a node's journal, a lane's entries of one index up to the current minute, one generation of a shard's LTX files), so none grows with the rest. Index keys start with the shard's lane, `index/reminders/{lane}/{minute}/{kind}/{id}/{base}.{n}` and `index/orphans/{lane}/{minute}/{kind}/{id}/{generation}` (`shard.Name.Lane`, a hash of the name), so each lane lists on its own. LTX files' keys do too, `data/shards/{lane}/{kind}/{id}/{generation}/{file}.ltx`, so the store's writes spread over 16 key ranges from the start. Manifests do too, `state/shards/{lane}/{kind}/{id}`, so a launch spike of claims spreads over the same 16 key ranges, though the node never walks them (every read is by the shard's name).

### Reminder index

An inactive shard's reminder needs someone to wake it. `next_reminder` in the manifest says when, and the index says which manifests to look at when: an entry is an empty object anyone can create, needing no owner and no clock, read only by the dispatcher. A minute is enough, since a shard's own loop fires at the second once it is active. It is one [due index](#reconcilers), and an entry's subject (see `internal/shardfile/reminder.go`) names the shard and the manifest version the entry backs, with a count of its moves.

- **Index first.** Before a manifest write that sets `next_reminder` to a new minute, the writer creates the entry for that minute and its base, a failed create failing the write. A write whose reminder is in the minute the manifest already has creates none.
- **Each write has its own entry.** An entry under another base never counts: two writes sharing one would let the dispatcher prune it on the first's terms while the second still relies on it.
- **The pruning rule.** An entry may be deleted when the manifest doesn't back it (absent, or `next_reminder` absent or after the entry's minute) and the manifest's current version is not the entry's base: the write the entry was made for replaces that version, so once the manifest has moved off it, the write has landed or can never land, while if the version is still the base the write may be in flight.
- **A backed entry is never deleted.** It is dispatched and moved forward, which covers a shard active after a dispatch whose node then crashes with nothing of it in the journal.
- **Anyone may apply the rule,** so several dispatchers at once or a zombie can't make it unsafe. Two dispatchers handling one entry leave at most a duplicate entry, dispatched once more and pruned once the reminder has fired, as a crash in a move does.

`specs/dispatch.qnt` checks that a shard with a reminder in its durable state always has a backed entry or a tail an adoption will still write a delta for.

### Orphan index

An orphan is an LTX file no manifest lists: an upload (a delta, a rebase's base or an adoption's delta) whose manifest update never lands, or a deleted shard's files when its node crashed between the manifest's delete and theirs. An orphan index entry says a generation of a shard may hold orphans, and almost every entry finds none. Its subject (see `internal/shardfile/orphan.go`) names the shard and the generation, and its minute is when the collector may first look: the write's minute plus the **age rule**, the journal's expiry (`Files.AgeRule`, set from `node.JournalExpiry`: a day, or four times the tail alert age if that is longer). By then no upload can still be on its way to a manifest, since a delta whose manifest update still fails has lost its tail anyway.

- **Index first.** Every LTX upload goes through one function (`Handle.putFile`), which creates the entry for the manifest's generation before the upload, and `DeleteShard` creates it before it deletes the manifest. A failed create fails the write before any of its files or its manifest change.
- **Two paths need none.** A rebase's deletes of the files it superseded are covered by the entry its base's upload made before the swap, which falls due an age later when the manifest lists the base alone. A start over moves off a manifest with no commits, so the old generation's files are uploads that never reached it, each with its own entry.
- **Writers never delete entries.** A create finds an existing one fine, so the writes of one generation in one minute share an entry, and only the collector deletes them.
- **The collector's rule.** For a due entry it reads the manifest, lists the generation's files (`GenerationPrefix`, so no other generation or shard) and deletes each `.ltx` file the manifest doesn't list (every one if the manifest is gone or names another generation) that is older than the age rule by the store's time, the lease checked before each delete. The age is checked on each file, whatever write made the entry, so a later upload into the same generation is never deleted early. An entry with no young unlisted file left is done, one with some moves to the minute after the youngest turns the age, a failure moves it 16 minutes later, and a failing lease check leaves it.
- **Anyone may apply the rule.** A file older than the age that is unlisted when the manifest is read can never be listed later, since a manifest only adds files its writer has just uploaded, so two collectors on one entry only delete orphans.

The index finds only what a path recorded, where a walk of every file finds orphans whatever left them, a bug included. So the fault tests keep the walk as an audit (`internal/audit`): after every scenario of the fault rig the node is stopped, the collector handles every entry as of a time past the age rule, and the walk of `data/shards/` fails on any LTX file older than the age that no manifest lists, which only a write path that made no entry first can leave.

## Reconcilers

Some of the node's work is the cluster's: waking the inactive shards whose reminders are due, and deleting the LTX files no manifest lists. Each is a **reconciler**, a due index and a handler for its entries, the shape of a Kubernetes controller (a work queue of keys and a handler that reads the truth and converges). One loop on every node runs them all, as one of the shardset's services, stopped with them before the shards are let go of. **A reconciler may be late, never wrong.**

- **The due index** (`internal/dueindex`). Its entries are empty objects keyed `{prefix}{lane}/{minute}/{subject}`, created by anyone, moved to a later minute and deleted, and listed per lane up to a minute, earliest first. The minute is when the entry is due, and the subject is the index's own (a shard and what it is for). An entry is a key, never a payload: the handler reads the truth (a manifest, a lease), so an entry handled twice or late is harmless. Handled entries leave the head of the listing, so no reconciler keeps a cursor or any state of its own, and a cold start, a change of runner and catching up after an outage are the same case.
- **The handler** gets one due entry and the node's lease check, does its work, checking the lease before each delete or send of its own, and answers what becomes of the entry: done (the loop deletes it), move (to a later minute, by the handler's own rule) or leave (it stays due, as when the pass's budget ran out or the lease check failed).
- **The loop** (`internal/reconcile`). Each reconciler passes on its own, at the next multiple of its interval on the clock when nothing is due (`Every`), again after a second when a pass found entries or the node has no listing of the cluster yet, and after a doubling wait up to a minute when a pass failed. A pass asks the ranking for the node's lanes, lists their due entries (one page shared over the lanes), hands them to the handler at most `InFlight` at once, at its `Rate` and within its `Budget`, and applies each answer, checking the lease before an entry's delete or move and writing nothing while it fails. The options are each reconciler's own.
- **Lanes and the ranking.** The work is split by [lane](#terms). For each lane every node ranks the live nodes of the lease scan's last listing by a rendezvous hash of the node's name and the lane (`reconcile.Runner`), and the first runs that lane for every reconciler. The nodes agree within a scan or two. While they don't (a node dying or joining) a lane has two runners or none for a few seconds, and a node joining or leaving moves only the lanes it ranks first for. Before its first listing a node runs nothing, and in a cluster of more nodes than lanes some nodes run none.
- **The rule.** A reconciler is idempotent and convergent: every write it makes is conditional or harmless to repeat, so two runners at once only cost work (an entry handled twice is deleted or moved twice), and none for a while only makes it late. A reconciler that couldn't follow the rule (an effect outside storage that must happen once, or decisions that fight when two nodes make them) would need an ownership record of its own, and none does.
- **Every reconciler is driven by entries.** One that ran on a schedule of its own or walked storage wouldn't fit the loop, and none does: work that needs doing is recorded by an entry before the write that makes it.

| Reconciler | Index | Passes | What it does |
|---|---|---|---|
| the dispatcher (`internal/reconcile/dispatch`) | the [reminder index](#reminder-index) | every minute | wakes the shards whose reminders are due while they are inactive |
| the collector (`internal/reconcile/collect`) | the [orphan index](#orphan-index) | every ten minutes, since its entries fall due a day after their write | deletes the LTX files no manifest lists |

For each due entry the dispatcher reads the manifest and prunes the entry by the rule above (done), or sends the backed shard a **dispatch**: `POST /_shardlite/activate` as the node's own request, with `Shardlite-Target` the shard and `Shardlite-If-Exists: true`. The node answers that path itself once the shard is held where the request lands, `200` if the request activated it and `204` if it was active already, and the app never sees it (the control and public listeners refuse every path under `/_shardlite/` they don't serve, and the peer listener takes one only from a node's forward). The request routes as any does: to the owner by the owner cache or the manifest, placed at random among the live nodes the dispatcher doesn't avoid when nobody live owns the shard, corrected by a `421`, and never creating the shard. The shard's own loop then wakes the app for its due reminders. A dispatched entry moves forward whatever the answer (16 minutes for a shard that was active, whose loop covers it, otherwise by a step doubling from a minute, the count of moves in its subject), and a failed manifest read leaves it.

A kind starting with `_` is reserved for the node (none is declared today): an app's declaration can't name one.

## Lifecycle

### Activation

1. **Owned by another node with a valid lease:** forward the request there.
2. **Unowned, or claimable after its owner's adoption:** claim by CAS and restore. A manifest with nothing to restore starts over in a new generation. A claim that loses its CAS to another node reads the manifest again and takes the path of a request that found another owner (forward to the winner, or `421` naming it for a forward), or answers `503` with `Retry-After: 0` if the manifest shows no owner yet. The app never saw the request, so it is never a `502`.
3. **No manifest:** a call creates it with a conditional create, which is the claim. A client request never creates a shard, so random ids from clients cost a manifest read and leave nothing behind.

**Placement** decides where steps 2 and 3 happen, after the manifest is read, so a shard active here, or owned by another live node, is never placed. A client's request and a call with no shard behind it (a login) claim on the node that received them, since the client's session is there. A call from a shard and a dispatch claim on a live node picked at random among the ones this node doesn't avoid (see [Routing and forwarding](#routing-and-forwarding)), since the caller's node is wherever the caller happens to live (and the dispatching node is whichever ranks first for the shard's lane), and a matchmaker would otherwise put every match on its own node. The node adds the pick to its owner cache and forwards the call, and the picked node claims or creates the shard as for any forward for an unowned shard, so one that finds another node has claimed it meanwhile answers `421`. A forward and a wake never place. A placement costs the picked node a second manifest read.

**Local files.** Every new local file gets a path of its own, `{kind}/{id}.{generation}.{random}.db` (`pathFor` in `internal/node/localfiles.go`). So no path is reused: the next claim of a shard whose old file an app still has open (a stop went ahead over it, or a start deleted it) gets a new file beside it, which is what makes it safe to delete a file the app has open (see [Letting go of a shard](#letting-go-of-a-shard)). The path an app is given in `Shardlite-File` therefore changes whenever the shard gets a new file (a restore, a claim). The node creates the file before it hands the path out in every case (a new shard's empty file, the renamed result of a restore, a start over), so the app opens it without create (`mode=rw`) and an open of a path that was deleted fails.

Concurrent requests share one activation, run by the shard's own loop. A shard deactivates after its kind's idle timeout unless a request, connection or due reminder holds it or the app still has its file open. It is released and its files are deleted (see [Takeover](#takeover)), and a shard holding nothing of the app's (never written, emptied, or carrying the delete marker) is deleted instead.

### Letting go of a shard

Deactivating or deleting a shard is only safe once nothing is writing to it, since a connection could still write to a file nobody captures. A request holds its shard, so once none does, the only thing that could write is a handle the app kept open, and the contract allows writes only during a request or a wake. The node asks SQLite's own lock: every connection holds a shared lock on byte 128 of the `-shm` file, tested with `F_GETLK` as SQLite does, after the node has closed every handle of its own (a process's `fcntl` locks drop with any descriptor, so it opens a shard's files only through capture), comparing the wal-index header before and after to catch a commit made just before the app closed.

A deactivation is the final sync and this check, then the one manifest update that records the last delta and gives the shard up, then the deletion of the files. Its release is asked again until its outcome is known, as [Takeover](#takeover) says.

If another process still has the shard open, capture resumes and the shard stays active, with nothing deleted: the idle path never goes ahead over an open file. A file deleted under an open handle loses the commits made through it without any signal, where a shard that stays active is served, its commits through the handle are captured, and the problem is loud. The shard stays until the app closes the file, and the next look after that lets it go.

Each look at a held shard is a whole release and resume (the reminders loop stops, the final sync, every handle closes, the `-shm` check, capture reopens), and a probe first would not make it cheaper: the check may only run once the node has nothing open on the shard, since closing a descriptor drops all of the process's `fcntl` locks on the file, capture's included. So the looks back off: the wait starts at the hold off (5 s) and doubles up to the kind's idle timeout, and a leak costs one release and resume per idle timeout. It starts over when a request uses the shard. And a pool that closes slowly is not a leak (Go's `database/sql` can keep a connection for up to about twice `SetConnMaxIdleTime`), so the node warns only once a hold has outlasted one more idle timeout, counted from the first look that found the file held. The warning names the shard and comes with a count (`Stats.HeldPastIdle`), once per hold. Both live in `idleState` in `internal/node/actor.go`.

Only a stop goes ahead over an open file. Once no request holds the shard (the public server is down, and a forward or call that arrives is placed elsewhere) it does the final sync and release with capture told to go ahead though another process holds the file, since the app is stopping too (the check of the wal-index header before and after still catches a commit made during it, which keeps the shard active and is tried again). The manifest is released in the one update and the files are deleted at once, held or not. The app's open handle keeps the inode until it closes it. Opening the old path again with `mode=rw` fails, and a commit through a connection that was already open succeeds on the deleted file and is lost, because SQLite in WAL mode doesn't notice a deleted database. That commit is the app's bug, since it broke both the idle timeout and the write rule, so the let-go logs a warning naming the shard and counts it (`Stats.LetGoHeld`), which is the loud signal. This is the one path that deletes under a handle. Holding SQLite's write lock on the deleted file so that such a commit fails was left out, and so was the park that would drop the holds (both are on the [roadmap](roadmap.md)).

A resumed release continues where capture left off when the WAL is the same one; if the app checkpointed and restarted the WAL instead, the uncaptured frames are gone, so the node writes the whole database as one file counted as one commit.

### Routing and forwarding

- **Forwards.** A request for a shard owned elsewhere goes to the owner's peer listener, never behind the load balancer, so node-only headers are trusted there, and shardless requests are never forwarded. The owner serves a forward as the original, carrying the origin, caller and hops. Gates stay where the writes are: the caller's on the caller's node, the callee's the owner's.
- **A forward is never forwarded again:** an owner that finds the shard isn't its own answers `421` naming the owner it found (the pick, for a claim a draining node placed elsewhere), and the forwarding node corrects its cache and answers `503` with `Retry-After: 0`. A forward of a client request for a shard that nobody owns is answered the same way, naming the forwarding node (`sendBack` in `internal/node/shardset.go`). Whoever owned the shard released it, at its idle timeout or at a stop, and the forwarding node's owner cache still names that node, so the client's session, which is at the forwarding node, is where the shard is claimed. Without this the shard would be claimed by the node it was forwarded to and, since the forwarding node's cache keeps naming that node, claimed there again after every release, pinned away from its clients. A draining node's forwards are the exception, since they carry `Shardlite-Placement: avoid` and are claims it placed here, and so is a manifest that still names this node (after a restart), which is claimed here since sending that back would bounce. The node never retries a request itself, keeping no bodies, so two stale nodes can't bounce one, and a forward failing after the owner acknowledged it is a `502`, since the app may have seen it.
- **Peer headers.** Two headers travel between nodes only, and are trusted only there: read on the peer listener's requests and from peers' answers, and taken out of answers before a client sees them. `Shardlite-Node` names the sender of a forwarder's request, which otherwise arrives as only an address with an ephemeral port (`origin.from` in `internal/node/server.go`). Answers don't carry it: the forwarder knows whom it forwarded to. `Shardlite-Placement` is an instruction about the sender, a Structured Fields Item (RFC 9651, parsed with `httpsfv`), the one value today the token `avoid`: place nothing here. A draining node sets it on every answer from its peer listener (the `102` included, which arrives first) and on its forwards; absence means the sender takes placements; parameters a node doesn't know are ignored, so an instruction can grow one (shedding, say) without a new header. A node keeps the peers it avoids, each entry with why it was learned: an answer from the peer carried `avoid`, or a forward from it did (it ends at an answer from the peer without the header, when the lease scan's listing no longer has the node live, or a lease TTL after the peer last said it, since the entry is hearsay and the listing can't tell a restart from a renewal), or a forward to the peer got no answer within the answer timeout (it ends at the next listing, or at any answer, and it covers the window after a stop for nodes that never exchanged traffic with the drainer while it drained). Entries for nodes the listing no longer has live are dropped when placement looks. **Placement** picks uniformly at random among the live nodes of the lease scan's last listing minus the avoid set, this node a candidate unless it is draining, and with no candidate at all the node claims for itself. Random is the whole criterion, because placement doesn't load-balance a cluster: a shard moves at its next idle (and there is no shard cache to be sticky against the choice), so what placement needs is only that new claims spread. A header that doesn't read (a name that isn't one, a placement value that isn't the token `avoid`, a value that doesn't parse) is counted (`Stats.BadPeerHeaders`), logged at Debug and ignored, so placement only gets worse for it, never wrong.
- **Finding the owner:** a bounded LRU hint, filled when a claim finds another owner and emptied by a `421`, by this node's own claim and by the lease scan finding a node dead. A stale entry costs one `503`, a miss one manifest read. Since every deactivation releases its shard, a stale entry is the normal case for a shard that went idle on the node the entry names: the next request through the node that holds it is forwarded, answered `421` by the node that released the shard, turned into a `503` with `Retry-After: 0`, and the client's retry reads the manifest and claims the shard there (see "A forward is never forwarded again" above). That is one client round trip per return of a shard last served elsewhere, on top of the claim and the restore, and the entry is corrected by it.
- **Fail fast:** the owner's node acknowledges every forward with `102 Processing` before its app sees anything, so a forward without an answer within a second never reached the app, and the forwarding node answers `503` with `Retry-After: 1`. The lease scan decides when the owner is dead: it empties the owner cache entries naming a dead node, so once the owner is dead the next attempt reads the manifest and either waits for the adoption (`503` with `Retry-After: 1`) or claims the shard.

### Reminders

The node knows nothing of what a reminder means: it reads one number from the shard's table and calls the app. While the shard is active its loop wakes the app (`POST /_shardlite/reminders`, in process, never forwarded) once the earliest due reminder is due and what the read saw is durable by the gate's rule, one wake at a time under a node-wide limit. While it is not, its index entry wakes it through the dispatcher. A reminder is always covered: in the tail until the next delta (adoption creates an entry due now for every tail it writes a delta for), and in the entry created before that delta afterwards. The `next_reminder` recorded with a delta must match the state the delta's files reach: anything committed beyond what was read means recording now instead, since it may have removed work the files hold. The node writes only the reserved table, at activation, and never a reminder.

## Concurrency

How the node's goroutines are owned, how they shut down and how they wait for each other. The per-part detail lives in `internal/node`; these are the rules it follows.

- **Every goroutine has an owner that joins it,** up to `Run`, which returns only after everything it started has ended. The long-lived parts are services (`internal/service`) run in groups, stopped by whoever started them, and one that returns before it is stopped has failed. Nothing restarts. Fork-join and the goroutines a service owns use `errgroup`, and the node has no bare `go` statement.
- **A goroutine waits only for goroutines it started, for its own I/O and for node-wide loops that never wait for their callers**, so waits can't form a loop: nothing `Shardset` depends on (the writer, the keeper, blob storage) waits for `Shardset`.
- **Callbacks from libraries never block on anything the node drives.** A callback runs to the end under the lock guarding the state it touches, and whoever started the work waits for durability afterwards.
- **The capture lock** guards a captured shard's WAL state, transactions, wal-index mapping and tail. Its holder runs to the end, so a sync is never cut off. No other lock nests, is held across I/O or a wait on another goroutine, or stands in for ownership. Semaphores are channels.

`Run` runs four stages, `front` (the public server and the services that depend on nothing), `callers` (the control and peer servers), `shardset` and `journal`. `journal` starts as soon as the lease is taken, so the lease is renewed while the rest is built, and every listener is bound before the other stages. The stages stop one at a time, in an order that depends on why the node stops:

- **A stop that was asked for** (the context ending, as on SIGTERM) drains first, then stops `front`, `shardset` and `journal`, releases the lease and only then stops `callers`. The control and peer listeners stay up while the shards are let go of, so a forward or call for a shard on its way out is answered by another node (`421` naming the pick for a forward) rather than met by a closed port.
- **A node that failed** (a service failed, the writer was fenced or the lease lost) stops `front`, `callers`, `shardset` and `journal` in that order, and keeps the lease. `callers` outlives `front` because a request holds a reference to its shard, and everything is joined before `shardset` lets go of its shards.

`journal` stops after `shardset` either way, since the shards write through the writer and need the lease.

### Shutdown

A stop that was asked for drains first (see [Takeover](#takeover)): readiness fails, `Shardlite-Placement: avoid` goes out and claims are placed elsewhere. `front` then stops: the public server stops accepting, waits up to 10 seconds for requests in flight and joins its handlers, which ends upgraded connections. `shardset` stops its loops and closes the table to new activations (a request that would start one and can't be placed elsewhere is refused with `503`), then lets go of every shard (256 at once, transient storage errors retried until a 30-second deadline). Each is one manifest write that records the final delta and `next_reminder` (its entry created first) and releases the shard, so a stop costs one write per active shard, and shards that went idle earlier were released then. A shard the app holds open is let go of at once, with a warning, because no request holds it. A shard a request still holds is tried again until the deadline, since the control and peer servers may have requests in flight, and once a shard has been held for the servers' grace period (10 seconds) `Run` stops those servers early, which ends requests that never end (a stream, a long poll, a WebSocket forwarded from another node). If the lease is gone or the writer is fenced, nothing is let go. `journal` stops, and `Run` releases the lease only if every shard was let go of and nothing is wrong, then stops `callers`. Each stop has its own deadline of at most 35 s, so a stuck part never holds up the rest, and a stop that is quiet takes seconds.

### Failures

`Node.Err` is nil while the lease is good and the writer isn't fenced, otherwise it is the reason. A panic crashes the node and adoption recovers its shards on the next start. The lease lost or the writer fenced stops at once, letting nothing go and keeping the lease. Any other service failing stops the node gracefully with its error. A listener that can't bind or shards that fail to build make `Run` return the error. Nothing restarts; a crashed shard that costs only that shard is on the [roadmap](roadmap.md).

## Garbage

LTX files no manifest lists are deleted by the collector, a [reconciler](#reconcilers), once an [orphan index](#orphan-index) entry the writer made first falls due. A rebase deletes the files it superseded itself, and a deleted shard's files go with it. Journal segments are each node's own to expire (see [Node journals and snapshots](#node-journals-and-snapshots)). Dead nodes' leases stay: a node of the same name starting again at epoch 1 would collide with its old files, and retiring leases is on the [roadmap](roadmap.md).

Local files have no collector. Every file the node stops needing (a deactivation, a failed activation, a deleted shard) is deleted at once, with one function (`removeLocal` in `internal/node/localfiles.go`, which also holds `deleteReleased` for a deleted shard and `cleanDataDir` for the start), whether or not an app has it open: an app's handle keeps the inode until it closes it, and no path is ever reused (see [Activation](#activation)). A start deletes every shard file left in the data directory, since after an OS crash none can be trusted to agree with blob storage, and a file an app still has open from before is deleted with the rest, so its shard activates at a new path with its data. A crash between steps leaves files that the next start deletes.

## The models

Each model in `specs/` is about one part of the code and assumes what the others check.

- `shard.qnt` is one shard: its file, its journal and when a reply may go out.
- `cluster.qnt` is ownership and adoption: leases, journals, fences, manifests and the claim rule, with storage alone as the truth.
- `dispatch.qnt` is the [reminder index](#reminder-index). It assumes the cluster: a crash leaves a tail to an adopter, and an adoption is an entry and then a delta.
- `capture.qnt` is the [read rule](#the-read-rule). It assumes SQLite: the WAL restarts only when every frame is copied into the database file, and a checkpoint copies a frame only past every reader's mark.

Only capture's traces are replayed against the code: `internal/capture/replay_test.go` plays each trace in `internal/capture/testdata/traces/` (made by `quint run --mbt --out-itf`, the command beside them) step by step against a real SQLite file and compares what capture promises, not the model's variables. The traces are committed so that `make test` needs no Quint. The cluster's models have no such seam in the code, which is spread over several packages.

## Testing

- **Fault injection** kills and fails the real `shardlite` binary, built with the `fault` tag (`e2e`, `fault_*_test.go`). The tag adds settings that exist in no other build (`SHARDLITE_FAULT_KILL_AT`, `SHARDLITE_FAULT_KILL_WHEN`, `SHARDLITE_FAULT_STORAGE`, `SHARDLITE_FAULT_TEMP`, `SHARDLITE_FAULT_PEER_HEADER`, `SHARDLITE_FAULT_MAX_FILES`; see `cmd/shardlite/fault.go`). A test arms a kill point (`internal/kill`) after the node is up, drives it through the e2e app and checks that every write a `storage` request acknowledged is in blob storage after a restore, which verifies every checksum, and that the database passes `integrity_check`. It covers crashes between every step of capture, snapshots and restore (in a random order too), apps that checkpoint themselves or reconnect all the time, failing storage (the creates of the journal's segments or of the orphan index's entries, the fourth field of `SHARDLITE_FAULT_STORAGE`) and temporary files, a node killed while it stops, after it has let go of its first shard (`fault_drain_test.go`, `kill.StopLetGo`: every acknowledged write is in blob storage, and every shard is served by the other node once it has adopted the dead one), and peer headers that two nodes drop or garble (calls still get through, and a value that doesn't read is ignored and counted in `Stats.BadPeerHeaders`). Every scenario of the fault rig ends with the [orphan index](#orphan-index)'s audit, which fails on an LTX file past the age rule that no manifest lists.
- **Fencing** is tested by killing nodes and by taking a live node's lease the way an adopter does while the node hears of nothing: a `storage` read must then fail and the node must stop, and a `none` read answers (`internal/node`, `TestHiddenPauseFailsStorageReads`). The clock check is tested with a proxy that moves the `Date` header of the store's responses (`internal/s3test`, `Skew`). Pausing and partitioning real processes is on the [roadmap](roadmap.md).
- **The protocol** is checked in Quint before it is implemented, and capture's model is replayed against the code. **Time** (lease expiry, timeouts) runs on `testing/synctest`'s fake clock.
