# shardlite roadmap

## Before a launch

What is left to make v1, in order, riskiest parts first. The one node and the cluster (leases, fencing, adoption, forwarding, reminders, drains) are built.

### Placement

- Placement and rebalancing from the counts in leases. Placement prefers the local node and otherwise picks from lease counts, since activation can't wait on a system shard. Rebalancing starts as a rule each node applies on its own: move only when clearly above average, cap its own moves per interval and pick targets at random among the less loaded nodes, so overloaded nodes don't all pick the same one. It chooses which shards to move by their request rate, prefers idle ones, doesn't move one again soon and skips ones an app holds open, and when one hot shard overloads a node it moves the node's other shards away rather than the hot one, which would only relocate the problem. A drain rebalances everything away before it stops, so its shards stay available while they move. Moving shards that are never idle (open WebSockets) means ending their connections after a deadline, if the policy needs to move them. Rebalancing moves ownership only; there is no data rebalancing beyond this. Placement also picks the node for a woken shard that has no owner, which for now the node responsible for waking it claims, so a node that let go of many shards with reminders (a large stop or eviction) takes them all back when they come due.

### Ready for a launch

- Load shedding with `503`, a cap on requests in flight per shard and `GOAWAY` for shedding HTTP/2 clients.
- The control API over TCP on Kubernetes. A DaemonSet node's localhost isn't reachable from app pods, so the node listens on the host's address and requires a token that it writes into the shared `hostPath` directory. Only pods on that host can read it, so `Shardlite-Caller` stays trustworthy. Without it, apps whose HTTP clients can't use Unix sockets have no control API on Kubernetes.
- A cap on activations in flight, answering `503` beyond it, against floods of requests for existing shards that each cost a restore.
- LTX files over S3's 5 GB limit for a single PUT, with multipart uploads (LTX files have unique names, so a plain multipart upload can replace the conditional create they use now).
- Distributed tracing with W3C trace context, and counting shardless requests that lead to calls to a shard.
- Metrics for everything the node does: requests, activations, flushes and gate waits, deltas and rebases, storage calls and leases.
- Hash prefixes on per-shard keys (`state/shards/7f/game.users/42`, and the same for LTX files), so a launch spike spreads over many S3 prefixes instead of hitting the limit per prefix (about 3,500 writes a second, raised only gradually) on `state/shards/`. Changing the key layout later means moving objects, so it should be settled before production data exists.
- Protocol versions for rolling node upgrades: each node publishes the range it speaks in its lease, and every request between nodes (forwards and dispatches) names the highest version both sides speak.
- Format versions for everything shardlite stores, with a marker per deployment that a node from an older release refuses, and a startup check that refuses a non-empty prefix without the marker.
- The `shardlite` command for operators: `ls`, `export`, `import` and `verify`, through the running node, or directly on blob storage when no lease is live.
- A crashed shard costs only that shard. A panic in a shard's own goroutines quarantines it (its requests get `503` and an alert is logged) while the rest of the node carries on, instead of crashing the process. Once no process has the file open, the node lets the shard go from its local file: a new base written from the file and swapped into the manifest by compare-and-swap, which holds every commit (including ones never captured) and supersedes the journal. The next request activates it as usual. Its reminders loop can restart on its own instead, since its state is rebuilt from the shard's tables.
- No uncaptured commits lost to a held file. A shard file that an app still has open across a restart is deleted once the app closes it, with whatever it committed that was never captured. Letting it go from the file, as for a crashed shard, keeps those commits.
- A soak test: the fault rig running for hours against a cluster, with kills, pauses, partitions, slow storage and restarts, checking the same guarantees as the per-scenario tests.
- A linearizability check of single shards under faults, as Jepsen does: clients record every read and write with its start and end, and a checker (Jepsen with Knossos, or Porcupine, which is in Go) confirms the history is linearizable per shard for kinds on the `storage` tier, while the fault rig kills, pauses and partitions nodes and skews clocks within the limit. Clocks pushed past the limit should show the node stopping rather than a violation, except on `storage`, whose reads hold under any clocks.
- What a store outage does to the cluster. The node's lease lives in blob storage, so a store it can't reach means it can't renew. The keeper lets the lease expire, the node stops and exits, and every node does the same, so the cluster is down until the store returns. Nothing in the design rides that out: a node that kept serving without a valid lease would be the zombie the lease exists to stop, and a timeout cannot tell a store outage from a partition to this node alone. What is worth working out before a launch: how fast the cluster comes back (the node could keep trying for its lease and its own adoption with backoff instead of exiting and leaving the restart to the supervisor, and a hundred nodes restarting should not be a herd), what the operator sees (a warning as soon as the store stops answering, well before the fuse, and a metric for it), and whether any narrow degraded mode is worth having, such as a stale read from the local copy, for kinds that can take one. The fault rig should have a scenario for it (the store refusing writes for a while) and check that nothing is lost and that the cluster comes back. The guide should say plainly that the cluster is as available as the store, less the lease TTL, and that the TTL is therefore also the store-outage tolerance, since a longer one rides out a blip and costs failover speed.

## Later

- Large shards: a rebase uploads the whole database, so shards of gigabytes may want a higher file limit or a middle level of merged deltas.
- Keeping the local cache across a node restart, for deployments where node redeploys are frequent or a cold cache is costly (large shards, or nodes redeployed with every app deploy as a sidecar). The node deletes its cache index and every shard file at each start, since after an OS crash neither can be trusted to agree with blob storage. Keeping them needs the index and the files made durable (the files at deactivation, or checked against the whole-database checksums the LTX files carry) and the app's files reconciled with storage at a start.
- Encryption and authentication of [traffic between nodes](#securing-traffic-between-nodes).
- A soft `max_bytes` per kind on how large its shards may grow, so one authenticated user cannot cost the cluster unboundedly: the node knows a shard's size at activation and after every delta, so it can warn, count and alert. Refusing to activate an oversized shard would strand it, so the cap stays soft.
- Checking tokens at the node, which closes the gap the [overview](overview.md#goal) names (a guessed id of a real shard costs a restore before the app can refuse it). The node gets a JWKS URL, issuer, audience and algorithm allow-list, and a kind with `"token": true` needs a valid token on a client request whose targets claim lists the target. The check runs after the public-kind check and before the owner cache or any blob read, and a failure answers `401`. The token still goes on to the app, so the node can refuse requests by token and never grant them. It would reword "the node never inspects credentials" in the [guide](guide.md#routing-requests-to-shards), so it is a design decision of its own.
- Optional modules (a matchmaker, inventory, purchasing) for apps to use, written in this repo and built into the node. A module is a package that declares its kinds in code like a system kind, under an app name of its own (`matchmaker.queue`), and is switched on by config, the same on every node of a version. It has handlers and reminder wakes and no goroutines of its own. Its design waits for the first module, which will show how it is switched on, whether it can serve public routes and where its secrets live (a login module needs the most care, since it holds provider secrets and parses untrusted tokens in the process that holds the lease).
- Schema versions reported by the app (`Shardlite-Version` on a response, or a reserved table row), opaque numbers that only go up, kept in the manifest. They are hints, never correctness. They give version-aware placement: during a rolling deploy, shards migrated by a new app version are never moved to nodes running an older one, which would refuse them with `503` until the node upgrades. Worth it if rolling deploys show that as a burst of errors. Down migrations, backfills and eager upgrades happen lazily as shards activate, and doing them in bulk would need a list of a kind's shards, which nothing keeps.
- Push streams: the node holds a push-only connection for the app, as SSE or a receive-only WebSocket (chosen by what the client asked for, the node answering pings and close frames and discarding anything else the client sends). The app handles the first request as usual and answers with `Shardlite-Stream: {id}`, the node keeps the connection and the app's own response ends, then the app pushes events and closes the stream with control API calls. The stream id names the node holding it, so a push from the shard's owner is forwarded there. Streams survive shard moves and app restarts, and an idle one doesn't keep its shard active. A client that wants to send makes ordinary requests, which have no order between them, so an app that needs one numbers its messages. WebSockets that carry client messages stay a pass-through.
- An [SDK](#sdk) in Go, then in Node and TypeScript to prove the contract is language-neutral, and others on demand.
- A journal store of its own, which is how a deployment gets fast durable answers: a tier of its own beside `none` and `storage`, waiting for a fast store instead of blob storage. The journal is the only write an answer waits for, it is small, and it needs only create if absent at `(node, seq)`, get, the highest number in use, delete below a number and a write id read back after a lost response, so the store is a drop-in backend behind the `internal/journal` interface and its conformance suite. S3 stays the default, and manifests, LTX files and leases stay in blob storage. Candidates are Postgres (or any SQL database with synchronous replication) and S3 Express One Zone (a bucket per zone, durable in one zone until the next delta). etcd and other peer-replicated stores don't fit, and DynamoDB, FoundationDB and Redis each fail on value limits or durability. Worth it if gate latency limits apps.
- A rebalancer as a system kind (`_system.rebalance/_cluster`), if rebalancing by each node alone herds onto the same targets or overshoots the cap. It advises and never commands: each node calls it every few seconds with its counts and it answers with a quota (move up to 3 shards to node-c), and the node still picks which shards to move. It needs the node to make calls of its own (the `fromNode` origin).
- Retiring the leases of nodes that never come back, for deployments whose node names churn (pod names), since every dead name stays in `state/leases/` and every lease scan lists it. A lease can't simply be deleted: a node of the same name would start again at epoch 1, where its new LTX files could collide with old ones, so the sweeper would move it to `state/retired/{name}` with its last epoch and `journal_next`, which `Acquire` reads.

## Later designs

Features from [Later](#later) that are designed in more detail.

### Securing traffic between nodes

v1 assumes the nodes are on a trusted private network. The options for encrypting and authenticating traffic between nodes:

- **Built-in mTLS from a shared cluster secret.** Every node derives the same CA from the secret and issues itself a node certificate. Setup is one secret in every environment.
- **Your own certificates** from cert-manager, Vault, step-ca or similar.
- **An encrypted network** (WireGuard, Tailscale) that already handles it, with shardlite staying unencrypted. This works on VMs, bare metal and Kubernetes with low overhead.

Service meshes (Istio, Linkerd) are not a target. They add two proxy hops to every call between nodes (roughly 0.5–1 ms), which is significant next to the forwarding budget. They also put a second proxy beside shardlite's own and only work on Kubernetes. In a cluster that already runs a mesh, shardlite's traffic between nodes should be excluded from it.

### SDK

A small library per language that makes the app contract hard to get wrong without hiding it. Everything stays plain HTTP and SQL, so apps without it keep working. It never opens databases or owns a pool: the driver is the app's choice (`mattn/go-sqlite3`, `modernc.org/sqlite` or `ncruces/go-sqlite3` in Go, `better-sqlite3` or `node:sqlite` in Node, `Microsoft.Data.Sqlite` in .NET), so the SDK works alongside it.

- **Request context.** From the request's headers (a map or a getter, so any framework can supply them): the shard the node opened (`kind`, `id`), its file, the caller, hops and whether the request is internal (it has `Shardlite-Caller`).
- **Routes, server side.** A route table where each route belongs to a kind and says how its id is computed from the request (path, payload, first gRPC message). An open-or-relay helper compares that shard with the opened one, hands the open file to the handler when they agree and otherwise relays the request to the right shard with `Shardlite-Relay: true`, passing the client's credentials on and streaming the answer back. Internal routes and reminder wakes skip the computation and take the opened shard.
- **Routes, client side.** Setting the target (header, `?shardlite-target=` for browser WebSockets, gRPC metadata) from the same names, per app, so requests reach the owner without a relay. A client that gets it wrong still works.
- **Opening shards.** The recommended pragmas as SQL to run on every connection the app opens, and the idle limit its pool must respect so deactivation isn't blocked (one call to `SetConnMaxIdleTime` in Go). The limit comes from the kind's `idle_timeout` in the declaration the app serves, so it is not a number the app keeps in step by hand. A helper that decides from `user_version` and `application_id` whether to migrate or refuse a shard, while migrations stay in the app's own tooling. It can share the node's migration loop (`internal/migrate`).
- **Writes.** With `BEGIN IMMEDIATE`, the app passes its transaction to the helpers below, and a `SQLITE_BUSY` from `BEGIN` means overload (`503`). With deferred transactions, a callback wrapper reruns the app's code on `SQLITE_BUSY`, so the callback must touch nothing outside the transaction.
- **Calls.** `call(target, method, path, body)` to the control API, copying the caller, hops and `traceparent` from the current request (timeouts stay the app's own, and an interceptor keeps `grpc-timeout`), with options for `Shardlite-If-Active` and `Shardlite-Sync`. For gRPC, a client interceptor that does the same, so generated stubs just work.
- **Reminders,** each taking the transaction (the app's own with `BEGIN IMMEDIATE`, or the one the wrapper passes to its callback), so they commit with the app's work: `set(key, due)` upserts a reminder and `cancel(key)` deletes it. A helper for the [durable send](guide.md#durable-send) records the call and its reminder together, and a handler wrapper for the wake loops over the due reminders, calls with the key as `Idempotency-Key`, deletes what succeeded and answers `503` otherwise. A receiver helper records `(caller, key)` and says whether the work was seen.
- **Durability.** `sync()` calls the control API, for purchases and other writes that must not be lost. `commitAndSync(tx)` commits an immediate transaction and then syncs, and the deferred wrapper takes an option to sync after its commit (outside its retries, since by then the commit has happened). A failure is a distinct error meaning the outcome is unknown, so the app doesn't acknowledge: it answers `503`, or the client retries with its idempotency key. Syncing a single HTTP response is a header the app sets itself (`Shardlite-Sync: storage`), so the SDK only exports its name.
- **Testing.** A fake for unit tests: call a handler with the headers set and a temporary SQLite file, then inspect the reminders and fire the wake by hand.
- **A single writer:** the [pattern](guide.md#a-single-writer) as a helper, with the epoch's table, an open that adds one to it, saves that check it and, for a process writing the file directly, the save counter and the confirm.

Go comes first and Node and TypeScript second, the language that differs most (async, a synchronous driver, no pool to leave alone), so the contract is checked against more than one shape. Each language has a framework-neutral core and thin adapters for its standard interfaces where it has them (`net/http` in Go, ASP.NET Core in .NET, WSGI and ASGI in Python), as OpenTelemetry does for the same problem. Where a language has several families, as Node and Java do, it gets adapters for the biggest and the core for the rest, and gRPC interceptors cover gRPC everywhere. Not included: an HTTP router (the route table sits beside the app's own), an ORM, a migration framework or retry policy for calls, which are the app's choices.

## Open questions

- **Flush interval.** It sets the loss window on a node crash (for shard kinds on the `none` tier), the latency of sync and the PUT rate per node. 250 ms for now.
- **WAL capture correctness.** Capturing frames from files another process writes is the riskiest part, already checked by `specs/capture.qnt`, the replay of its traces and the fault tests. Litestream's open issues in this area (external checkpoints, WAL resets) are worth reading as cases to test.
- Tail age limit and file limit: shorter tails mean faster recovery after a crash, at the cost of more deltas, and rarer rebases mean more files per restore.
- Node lease TTL: short enough for fast failover, long enough to survive VM pauses and network blips, and the same margin is how long a store outage the cluster rides out before every node stops.
- **Regions.** v1 is one region. Region-locked games run a separate cluster per region and send players to theirs at login. Global games (a guild with members in EU and NA) would need more. Each shard would have a home region in the manifest, set at creation (where it was first written, or from a hint). Requests from other regions would be forwarded, and moves between regions would be explicit, since blob storage is regional. Data residency would pin a shard's region.
- **Throughput of a hot shard's wake.** There is one wake per shard at a time, and its handler handles each due reminder in a transaction of its own, so SQLite's single writer meets the app's own requests there. A hot shard (a leaderboard, a matchmaking queue) with many reminders due together may do better with a handler that takes several due rows in one transaction. To measure with the bench: a shard with 1,000 reminders due at once, handled one per transaction and in batches of 10 and 100, with the app's own writes running, with and without `BEGIN IMMEDIATE` in the handler.
